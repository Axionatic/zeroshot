# Upstream v6.46 Reconciliation Design

**Status:** Approved decisions consolidated for implementation planning

**Date:** 2026-09-02

**Authority:** ADRs 0001-0015 and
`docs/2026-08-31-upstream-v6.46-reconciliation-report.md`

## Purpose

Reconcile the internal Zeroshot fork from the PR 31 squash tip
`1bc71f6881da82de9f28dc5c78107a9151ed24c0` onto authoritative upstream
v6.46.0 at `e73727662df53bbaf8aad8ba9e489d2c76a79499`, retain the selected fork
products and safety behavior, and deliberately discard superseded mechanisms.
The result remains an internal Node-first product. It imports and verifies the
entire upstream Node, Rust, protocol, target, and Python workspace but never
publishes the fork or activates the native product for routine use.

This design separates three kinds of work:

1. a byte-identical upstream baseline and history bridge;
2. reconciliation adaptations required before that baseline can replace fork
   `main`; and
3. independently reviewable post-reconciliation features for subagent
   visibility and prompt JSON minification.

The separation is intentional. In particular, telemetry is absent at the
reconciled-baseline checkpoint rather than carried forward as disabled legacy
code.

`https://github.com/the-open-engine/zeroshot.git`. The old `covibes/zeroshot`

## Global constraints

- Node.js 22 or newer is required by upstream.
- The maintained TypeScript sources in `src/legacy-lib/` and other upstream
  TypeScript source roots are authoritative; generated `lib/` output is never
  hand-edited.
- Rust protocol projections are regenerated from their Rust authority; checked
  JSON and TypeScript projections are never resolved by hand.
- The existing `zeroshot` command and `~/.zeroshot` / repository `.zeroshot`
  state locations remain unchanged.
- No implementation or verification step may invoke a live model/provider
  without explicit permission.
- No plan step may push, merge to shared `main`, publish, install a native CLI,
  configure hosted endpoints, or enable release credentials without separate
  authority.
- Upstream generic workflows remain the default. The three fork workflow packs
  are opt-in.
- Required handoff gates are never bypassable by preflight options.
- Telemetry is observational and may never change task, retry, provider,
  session, output, or terminal outcomes.
- Every bounded workflow emits exactly one terminal event.

## Reconciliation topology

### History-only bridge

Create the implementation worktree from the pinned upstream commit, then use
the `ours` merge strategy to make the fork tip reachable without importing any
old fork tree content:

```bash
git merge --no-ff --strategy=ours \
  1bc71f6881da82de9f28dc5c78107a9151ed24c0 \
  -m "merge: bridge internal fork history onto upstream v6.46.0"
```

The bridge commit must have two parents, contain a tree byte-identical to
`e737276`, make both pinned tips ancestors, and report `79 0` for
`HEAD...upstream/main`. This avoids an ambiguous 24-file conflict resolution
and prevents obsolete fork patches from silently surviving.

All retained behavior is then reimplemented against v6.46 interfaces as
reviewed adaptation commits. A backup ref named `backup/pre-v6.46-main` must
point at the exact fork tip before reconciliation begins.

### Checkpoint sequence

1. **B0 — pinned upstream:** upstream v6.46 tree and clean full baseline.
2. **B1 — history bridge:** identical tree, both histories reachable, `79 0`.
3. **B2 — reconciliation foundation:** internal-release guard, Node-active /
   native-latent policy, security ports, iteration and terminal lifecycle.
4. **B3 — quality and operations:** approved preflight gate and closed runtime
   operation boundary, with no generic command trigger.
5. **B4 — workflow products:** all three packs, bounded outcomes, deterministic
   output, fixed batching.
6. **R — reconciled baseline:** complete verification and user review; eligible
   to replace internal `main` only with separate approval.
7. **T — telemetry feature branch:** Claude and Codex foreground visibility.
8. **P — prompt-format feature branch:** minified JSON with full ISO timestamps.

T and P branch from R and are independently reviewable. They need not be
merged in either order.

## Upstream identity and internal publication policy

Adopt upstream's package name, repository references, docs, update checker,
release topology, lockfiles, and generated artifacts. Do not retain the old
Covibes product identity or accidentally install upstream's legacy Covibes npm
bridge.

Publication protection uses the approved option 1: preserve upstream release
workflows and dry-run jobs, but add an explicit canonical-repository condition
to every mutating release job. A publishing or recovery job can run only when:

```yaml
github.repository == 'the-open-engine/zeroshot'
```

The condition belongs on the job itself and is combined with the existing
event/action conditions. It is required on:

- `.github/workflows/release.yml`: `release`, `recover`;
- `.github/workflows/release-rust.yml`: `rust-image-publish`, `rust-publish`,
  `rust-shim-publish`, `python-sdk-release`; and
- `.github/workflows/release-python.yml`: `publish`.

Build, test, package, manifest, and dry-run jobs stay usable in the internal
fork. A repository-policy test parses all release workflows and fails if a
known publishing primitive or reusable release call is reachable from a job
without the canonical-repository guard. Repository secrets, trusted publishers,
registry tokens, and GitHub environments are not configured in this fork.

## Product activation boundary

The Node CLI remains the only routine product:

- `zeroshot` and existing shell helpers continue to resolve to the Node CLI;
- the Rust workspace, native distribution, protocol, hosted target, and Python
  SDK are built and tested;
- no postinstall, setup wizard, alias, package script, Docker default, or docs
  change redirects ordinary runs to `zeroshot-rust`;
- no hosted endpoint or native target is configured by reconciliation; and
- native activation is revisited only after upstream declares it stable and
  supported.

This is a runtime policy, not permission to delete upstream native sources.

## Reconciliation foundation adaptations

### Hook VM hardening

Port the fork's sandbox hardening into upstream
`src/agent/agent-hook-executor.js`. Compile hook logic with
`vm.compileFunction` in strict mode and expose only the existing bounded
sandbox API. Do not interpolate untrusted script text into a wrapper function.
Regression tests must attempt constructor/host-realm escape paths and prove
the sandbox does not acquire `process`, `require`, or host globals.

### Trigger-producer reachability

In `src/config-validator.js`, an `onComplete` contract is valid only when the
agent has an executable `execute_task` producer path. Configuration validation
must reject unreachable completion contracts without rejecting validators and
other legitimate no-task roles that do not advertise completion output.

### Logical iteration accounting

In `src/agent/agent-lifecycle.js`, increment `agent.iteration` once for each
logical trigger execution, not once for each provider retry. Provider retry,
recovery, continuation, and terminal bounds stay upstream-owned. Reaching the
maximum enters an explicit synthesis/terminal phase rather than scheduling a
global delayed stop.

### Exactly-one terminal lifecycle

Review and drafting packs require time to synthesize their bounded final
artifact. Represent that as an explicit lifecycle phase with a bounded
deadline. A success, max-iteration, synthesis failure, cancellation, or fatal
error converges on one idempotent terminalization boundary which publishes
exactly one terminal event. Do not restore the fork's old ten-minute delayed
stop timer.

### Claude overlay fail-closed behavior

Retain upstream's owned, private, per-run Claude settings overlay in
`src/worktree-claude-config.ts`. It must remain owner-checked, mode-checked,
canonical-path checked, and cleanup-owned. If the small hardening is still
needed, make `isMutableRecord` reject arrays. Malformed input fails closed; it
is never replaced with an empty settings object. Do not restore global
settings installers.

## Approved preflight quality gate

### Purpose and separation

The preflight gate is an optional, cheap Node-side check of the starting
repository. It runs before any provider/model call. It is not a command proof,
not a protected handoff gate, and not evidence that remains valid after a
workflow changes the tree.

Implementation workflows may additionally use their owned pre-validation
phase after implementation and before validators. Protected
`requiredQualityGates` remain enforced by the upstream handoff boundary and
have no bypass.

### Data model

Store one approved record per canonical repository root under the existing
`~/.zeroshot/projects/` state directory. Use a versioned record:

```ts
interface ApprovedPreflightGateV1 {
  version: 1;
  repositoryPath: string; // realpath of canonical git root
  command: string; // exact human-approved shell command
  fingerprint: string; // sha256 of discovery inputs + command
  discovery: 'deterministic' | 'manual';
  approvedAt: string; // full ISO-8601 timestamp
}
```

Configuration filenames remain keyed by the SHA-256 hash of the canonical
repository path, preserving the fork's existing external state location while
making the record explicit and fail-closed. A malformed, mismatched-path, or
unknown-version record is treated as no approved gate.

### Discovery and approval state machine

`discoverPreflightGate(repositoryRoot)` is deterministic and side-effect free.
It inspects bounded, known ecosystem files and returns either one composed
command plus its input fingerprint or no suggestion. It must not invoke a
model, execute package scripts, scan outside the repository root, or write
state.

Before provider startup:

1. `--skip-quality-gate` returns `skipped` without discovery or execution.
2. A valid cached record whose fingerprint still matches executes immediately.
3. A new or changed deterministic suggestion in an interactive TTY is shown
   verbatim and requires one-time confirmation before it is cached or run.
4. A new or changed suggestion in a non-interactive run fails before provider
   startup unless `--allow-missing-quality-gate` is explicit.
5. No cached record and no deterministic suggestion is the same missing-gate
   state: interactive runs may continue after an explicit no-gate confirmation;
   unattended runs require `--allow-missing-quality-gate`.
6. Refusal, gate failure, timeout, cancellation, or launch error aborts before
   any provider call.

LLM-assisted discovery, if later exposed, may only print a suggestion for a
human to copy into the same approval flow. It never caches, authorizes, or
executes its answer.

### Execution boundary

The runner receives a validated record and canonical root, then invokes the
approved command in that root with:

- a fixed timeout;
- cancellation propagation;
- bounded captured stdout and stderr with truncation markers;
- a minimal inherited environment with known secret-shaped values redacted
  from diagnostics;
- no template-controlled environment or cwd; and
- a structured result (`passed`, `failed`, `timed_out`, `cancelled`, or
  `launch_error`).

The approved command is intentionally a shell string because the human is
approving the exact repository gate. No template can set it. The implementation
must not reuse `execute_system_command` or expose this runner as a trigger
action.

### Launch-path propagation

Add both CLI flags to the maintained run-option types and serialize them
through foreground, detached daemon, worktree, Docker, resume, and trusted
worker boundaries. The gate runs once against the original repository before
isolation setup or a model call. Daemon children consume a persisted preflight
receipt rather than rediscovering or prompting.

`--skip-quality-gate` and `--allow-missing-quality-gate` affect only this
preflight subsystem and optional pack pre-validation. They are never mapped to
or allowed to remove `requiredQualityGates`.

## Closed workflow-operation boundary

### Why a separate boundary exists

The historical `execute_system_command` action served two unrelated purposes:
quality checks and deterministic artifact/context processing. Quality checks
move to the dedicated boundaries above. The remaining behavior becomes typed,
in-process runtime operations, so templates cannot name executables, pass
shell, select cwd, inject environment variables, or route arbitrary stdout.

### Trigger contract

Add one closed action to configuration validation and hook execution:

```ts
type WorkflowOperationId =
  | 'review.synthesize'
  | 'document.build_revision_context'
  | 'document.assemble';

interface ExecuteWorkflowOperationAction {
  action: 'execute_workflow_operation';
  operation: WorkflowOperationId;
}
```

No `command`, `args`, `cwd`, `env`, `stdin`, `onSuccess`, or `onFailure`
routing field is accepted. Each registered operation owns its input topics,
ledger queries, output schema, success topic, failure topic, and whether the
result is terminal. Unknown IDs and extra fields fail configuration validation.

### Runtime interface

```ts
interface WorkflowOperationContext {
  clusterId: string;
  agentId: string;
  triggeringMessage: Message;
  ledger: LedgerReader;
  signal: AbortSignal;
  now(): Date;
}

interface WorkflowOperationResult {
  topic: string;
  content: { text: string; data: Record<string, unknown> };
  terminal: boolean;
}

type WorkflowOperation = (context: WorkflowOperationContext) => Promise<WorkflowOperationResult>;
```

The registry is a frozen record keyed by `WorkflowOperationId`. Operation
results pass through the ordinary message bus and the common terminalization
boundary. Exceptions are bounded, redacted, and converted to the operation's
owned failure event; they do not crash the orchestrator or execute fallback
shell.

### Owned operations

- `review.synthesize` reconstructs analyst/validator history and produces one
  Markdown review artifact with confirmed, contested, and withdrawn findings,
  validator notes, severity changes, statistics, and readiness.
- `document.build_revision_context` reconstructs the current document and
  aggregates only the latest validator round into the next drafter context.
- `document.assemble` deterministically applies the full first draft plus later
  deltas, adds notes and unresolved validator reasons, and produces one
  Markdown document artifact.

The old `scripts/write-review-report.js`, `scripts/build-revision-context.js`,
`scripts/assemble-doc.js`, `scripts/quality-gate-runner.js`, and generic
`execute_system_command` tests are prior art. Their shell/stdin/environment
protocols are not retained.

## Specialized workflow packs

### Shared pack contract

Restore code review, documentation review, and document drafting under
`cluster-templates/` as parameterized opt-in configurations. Each family has a
base plus its named specialists and conductor. Generic upstream templates and
`conductor-bootstrap.json` remain unchanged as defaults.

All packs share:

- explicit schemas for every inter-agent message;
- deterministic topic and producer reachability;
- a conservative fixed batch limit;
- no autocompact environment injection;
- no generic command trigger;
- a bounded analyst/revision count;
- an explicit synthesis phase and exactly one terminal event;
- simulation coverage for random ordering and topology; and
- a declaration that the successful result is exactly one Markdown artifact.

Adaptive concurrency is excluded. A later design may reserve four machine
threads and preserve a two-worker floor, but must also consider provider,
harness, memory, and configured maxima.

### Code-review pack

Restore the base workflow and Bell, Book, Candle, and conductor roles. Analysts
produce candidate findings; validators may confirm, contest, withdraw, or
adjust severity. At the iteration cap, synthesize the truthful report rather
than assuming approval:

- any contested finding makes the overall result `NOT_READY`;
- confirmed, contested, and withdrawn sections remain distinct;
- validator reasons and severity changes remain visible; and
- the cap is a normal bounded terminal reason, not a validation verdict.

Zero findings must produce a valid, explicit ready report rather than waiting
for a message that can never be produced.

### Documentation-review pack

Restore the base workflow and Trace, Vector, Axiom, and conductor roles. It
uses the same contested-finding terminal semantics as code review, but its
finding schema and prompts are documentation-specific. The two pack families
share synthesis primitives, not templates or message schemas.

### Document-drafting pack

Restore the base workflow and Facet, Lens, Prism, and conductor roles. The first
`DRAFT_READY` owns the complete document; later iterations contain explicit
deltas. Reconstruction order is deterministic and stable across retries.

If validators unanimously approve, assemble an `ALL_APPROVED` artifact. If the
revision cap is reached, assemble the best document with termination
`MAX_ITERATIONS` and append conspicuous unresolved sections containing each
validator verdict and reason. The incomplete draft remains useful but is never
labelled approved.

## Deterministic `--output` contract

`zeroshot run --output <file>` is separate from upstream's foreground benchmark
`--result-file`. It is accepted only when the fully resolved configuration
declares exactly one Markdown artifact.

At the initial CLI boundary:

1. capture the original invocation cwd;
2. resolve a relative destination against it;
3. append `.md` only when the final path component has no extension;
4. reject incompatible workflows before provider startup; and
5. persist the absolute destination in run state for foreground, detached,
   resumed, worktree, and Docker paths.

On successful terminal artifact production, write to a private sibling
temporary file, fsync/close as supported, then rename atomically over the
destination. Create missing parent directories. On failure, cancellation,
invalid/multiple artifacts, or non-success terminalization, remove only the
owned temporary file and leave any existing destination unchanged. Print the
resolved path after a successful commit.

Artifact persistence is an orchestrator/runtime responsibility, not an
operation script side effect. The operation returns Markdown in its typed
result; the artifact writer owns filesystem mutation.

## Post-reconciliation subagent visibility

### Activation

Compute one immutable capability before the first provider launch:

```ts
interface SubagentTelemetryCapability {
  enabled: boolean;
  reason:
    | 'foreground_tty'
    | 'detached'
    | 'daemon'
    | 'silent'
    | 'worker'
    | 'non_tty'
    | 'unsupported_provider';
}
```

Only a run launched in a supported foreground TTY with the status footer gets
`enabled: true`. Later attach, `logs -f`, detached, daemon-only, silent, and
worker paths never create telemetry files or install tracking hooks.

### Provider-neutral event sink

Use a Zeroshot-owned per-run directory with private permissions and one
append-only JSONL file per parent agent. The normalized record is:

```ts
interface SubagentLifecycleEvent {
  version: 1;
  event: 'start' | 'stop';
  provider: 'claude' | 'codex';
  parentAgentId: string;
  childAgentId: string;
  agentType: string;
  title?: string;
  occurredAt: string; // full ISO-8601
}
```

The hook writer validates fixed-size stdin, event name, scalar lengths, parent
identity supplied by the owned overlay, output path containment, ownership,
mode, and regular-file status. It appends one bounded record. Invalid telemetry
exits successfully without affecting the provider.

The consumer reads only complete newline-terminated records, caps file size,
record size, active children, displayed rows, and retained stopped entries,
and deduplicates transitions by `(provider, parentAgentId, childAgentId)`.
Partial/malformed/late records are ignored or retained for the next read.
Parent completion stops any still-active child in memory before owned cleanup.

### Claude producer

Extend the existing `src/worktree-claude-config.ts` overlay only for an enabled
run. Merge Zeroshot's `SubagentStart` and `SubagentStop` commands into the
owned overlay without mutating user files or dropping unrelated settings.
Claude's documented hook events supply `agent_id` and `agent_type`; transcript
paths and final messages are deliberately ignored.

Claude `SubagentStart` does not expose the spawning Agent tool's description.
Use a terse title only when a separately captured, bounded `PostToolUse` Agent
record can be correlated unambiguously to one child. Concurrent ambiguity falls
back to `agent_type`. No transcript parsing is permitted.

### Codex producer

Create an owned Codex config layer beside the run's private config, using
documented `hooks.json` or inline hook configuration and the existing adapter's
`--config` support. Codex discovers hooks from active config layers and still
runs matching hooks from other layers; Zeroshot must not suppress or bypass
their review/trust behavior.

Use documented `SubagentStart` and `SubagentStop` records for lifecycle. To get
the orchestrator-assigned `task_name`, observe the owned `PostToolUse` record
for `spawn_agent` and correlate its returned child identifier. If a provider
version cannot provide safe correlation, show `agent_type`. Do not restore PR
31's incidental JSON collaboration-stream parser.

Hook support is capability-detected. Unsupported or disabled hooks yield no
child rows and do not fail the run.

### Footer integration

Feed normalized child state into the existing `StatusFooter`; do not create a
second renderer. Child rows are visually subordinate to their direct parent,
show a bounded title/type and elapsed state, and do not participate in process
metrics sampling. Footer row caps and terminal-size degradation remain
upstream-owned.

### Provider documentation

Implementation must re-check the official hook contracts at execution time:

- OpenAI Codex: <https://learn.chatgpt.com/docs/hooks>
- Claude Code: <https://code.claude.com/docs/en/hooks>

As of this design, both document `SubagentStart`/`SubagentStop` with child ID
and type. Codex also documents layered hook discovery and concurrent matching
hooks. These are versioned external capabilities, so fixtures must be literal
and unsupported versions must degrade safely.

## Post-reconciliation prompt JSON minification

Restore only mechanical JSON compaction at maintained prompt-assembly
boundaries. Replace pretty-printed embedded JSON with `JSON.stringify(value)`
while preserving object/array content, ordering, surrounding instructions, and
full ISO-8601 timestamps. Do not abbreviate dates and do not reapply the fork's
terse/calm wording in this change.

Rendering tests compare parsed embedded JSON and assert that indentation-only
whitespace is absent. Snapshot/golden changes must show no semantic prompt text
change. Calm/non-escalatory wording remains a future behavioral project
informed by Anthropic's emotion-concepts research, not part of reconciliation
or minification.

## Explicit exclusions

- No adaptive machine-thread concurrency in this program.
- No `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` injection.
- No abbreviated timestamps.
- No calm/terse prompt rewrite.
- No generic `execute_system_command` or template-controlled subprocess.
- No use of the upstream external `cmdproof` product as the active Node
  preflight gate.
- No native/Rust CLI activation, hosted endpoint configuration, protocol fork,
  or routine install.
- No global Claude or Codex settings mutation.
- No transcript parsing for subagent titles.
- No Codex collaboration JSON observer.
- No public publication or release-secret activation.

## Verification and acceptance

### Structural acceptance

- The bridge tree equals `e737276` and both pinned tips are ancestors.
- The post-bridge count is exactly `79 0`; final count is `79 + N, 0`.
- No generated file is hand-edited when a generator owns it.
- All old fork commits are reachable through the bridge, with prior-art-only
  PR 31 source commits documented but not merged.

### Behavioral acceptance

- Existing generic workflows behave as upstream by default.
- All three opt-in packs validate, simulate, terminate, and emit their truthful
  Markdown artifact across success, zero-result, retry, cap, and failure paths.
- `--output` is atomic and consistent across foreground, detached, resumed,
  worktree, and Docker paths.
- A cached approved preflight runs before all provider calls; new/changed gates
  prompt once; unattended missing gates need the narrow flag.
- Neither preflight flag can bypass `requiredQualityGates`.
- Generic command actions and their shell/environment protocol are absent.
- Hook sandbox breakout, unreachable producer, retry iteration, synthesis
  deadline, and exactly-one-terminal regressions pass.
- Public publishing jobs are canonical-repository guarded; dry runs remain
  available.
- Native sources build and test but are not activated.
- Telemetry, when enabled on its later branch, is foreground-only, bounded,
  provider-neutral, overlay-contained, best-effort, and absent from other
  launch modes.
- Prompt minification, on its later branch, changes only mechanical JSON
  whitespace and retains full ISO timestamps.

## Cutover record

Before asking to replace internal `main`, record:

- exact bridge and final commit IDs;
- exact `N` and final ahead/behind count;
- each verification command, exit status, and any environmental skip;
- proof that all mutating release jobs carry the canonical guard;
- proof that the installed `zeroshot` and shell helpers still resolve to Node;
- absence of publication credentials/configuration introduced by the branch;
- unresolved review findings; and
- separate branch/commit references for telemetry and prompt minification, if
  implemented.

Cutover, push, publication, and activation remain separate user decisions.
