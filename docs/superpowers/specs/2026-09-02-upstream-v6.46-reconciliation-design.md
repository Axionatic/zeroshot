# Upstream v6.46 Reconciliation Design

**Status:** Approved decisions consolidated for implementation planning

**Date:** 2026-09-02

**Authority:** ADRs 0001-0015 and
`docs/2026-08-31-upstream-v6.46-reconciliation-report.md`

## Purpose

Reconcile the internal Zeroshot fork from the PR 31 squash tip
`1bc71f6881da82de9f28dc5c78107a9151ed24c0` onto authoritative upstream
v6.46.0 at `e73727662df53bbaf8aad8ba9e489d2c76a79499`, retain the selected fork
products and safety behavior, and deliberately discard superseded mechanisms.
The result remains an internal Node-first product. It imports and verifies the
entire upstream Node, Rust, protocol, target, and Python workspace but never
publishes the fork or activates the native product for routine use.

This design separates three kinds of work:

1. a byte-identical upstream baseline and history bridge;
2. reconciliation adaptations required before that baseline can replace fork
   `main`; and
3. independently reviewable post-reconciliation features for subagent
   visibility and prompt JSON minification.

The separation is intentional. In particular, telemetry is absent at the
reconciled-baseline checkpoint rather than carried forward as disabled legacy
code.

## Global constraints

- Node.js 22 or newer is required by upstream.
- The maintained TypeScript sources in `src/legacy-lib/` and other upstream
  TypeScript source roots are authoritative; generated `lib/` output is never
  hand-edited.
- Rust protocol projections are regenerated from their Rust authority; checked
  JSON and TypeScript projections are never resolved by hand.
- The existing `zeroshot` command and `~/.zeroshot` / repository `.zeroshot`
  state locations remain unchanged.
- No implementation or verification step may invoke a live model/provider
  without explicit permission.
- No plan step may push, merge to shared `main`, publish, install a native CLI,
  configure hosted endpoints, or enable release credentials without separate
  authority.
- Upstream generic workflows remain the default. The three fork workflow packs
  are opt-in.
- Required handoff gates are never bypassable by preflight options.
- Telemetry is observational and may never change task, retry, provider,
  session, output, or terminal outcomes.
- Every bounded workflow emits exactly one terminal event.

## Reconciliation topology

### History-only bridge

Create the implementation worktree from the pinned upstream commit, then use
the `ours` merge strategy to make the fork tip reachable without importing any
old fork tree content:

```bash
git merge --no-ff --strategy=ours \
  1bc71f6881da82de9f28dc5c78107a9151ed24c0 \
  -m "merge: bridge internal fork history onto upstream v6.46.0"
```

All bridge and adaptation commands run from the newly created reconciliation
worktree, never from the planning checkout. Before the baseline and before each
mutating task, assert the canonical worktree root, current branch, clean state,
and expected HEAD.

The bridge commit must have two parents, contain a tree byte-identical to
`e737276`, make both pinned tips ancestors, and report `79 0` for
`HEAD...upstream/main`. This avoids an ambiguous 24-file conflict resolution
and prevents obsolete fork patches from silently surviving.

All retained behavior is then reimplemented against v6.46 interfaces as
reviewed adaptation commits. A backup ref named `backup/pre-v6.46-main` must
point at the exact fork tip before reconciliation begins.

### Checkpoint sequence

1. **B0 — pinned upstream:** upstream v6.46 tree and clean full baseline.
2. **B1 — history bridge:** identical tree, both histories reachable, `79 0`.
3. **B2 — reconciliation foundation:** internal-release guard, Node-active /
   native-latent policy, security ports, iteration and terminal lifecycle.
4. **B3 — quality and operations:** approved preflight gate and closed runtime
   operation boundary, with no generic command trigger.
5. **B4 — workflow products:** all three packs, bounded outcomes, deterministic
   output, fixed batching.
6. **R — reconciled baseline:** complete verification and user review; eligible
   to replace internal `main` only with separate approval.
7. **T — telemetry feature branch:** Claude and Codex foreground visibility.
8. **P — prompt-format feature branch:** minified JSON with full ISO timestamps.

T and P branch from R and are independently reviewable. They need not be
merged in either order.

## Upstream identity and internal publication policy

Adopt upstream's package name, repository references, docs, update checker,
release topology, lockfiles, and generated artifacts. Do not retain the old
Covibes product identity or accidentally install upstream's legacy Covibes npm
bridge.

Publication protection uses the approved option 1: preserve upstream release
workflows and dry-run jobs, but add an explicit canonical-repository condition
to every mutating release job. A publishing or recovery job can run only when:

```yaml
github.repository == 'the-open-engine/zeroshot'
```

The condition belongs on the job itself and is combined with the existing
event/action conditions. It is required on:

- `.github/workflows/release.yml`: `release`, `recover`;
- `.github/workflows/release-rust.yml`: `rust-image-publish`, `rust-publish`,
  `rust-shim-publish`, `python-sdk-release`; and
- `.github/workflows/release-python.yml`: `publish`.
- `.github/workflows/publish-covibes-bridge.yml`: `publish-bridge` (disable or
  guard the real-publish path; do not install the legacy bridge).

Build, test, package, manifest, and dry-run jobs stay usable in the internal
fork. A repository-policy test parses all release workflows and fails if a
known publishing primitive or reusable release call is reachable from a job
without the canonical-repository guard. Repository secrets, trusted publishers,
registry tokens, and GitHub environments are not configured in this fork.

## Product activation boundary

The Node CLI remains the only routine product:

- `zeroshot` and existing shell helpers continue to resolve to the Node CLI;
- the Rust workspace, native distribution, protocol, hosted target, and Python
  SDK are built and tested;
- no postinstall, setup wizard, alias, package script, Docker default, or docs
  change redirects ordinary runs to `zeroshot-rust`;
- no hosted endpoint or native target is configured by reconciliation; and
- native activation is revisited only after upstream declares it stable and
  supported.

This is a runtime policy, not permission to delete upstream native sources.

## Reconciliation foundation adaptations

### Hook VM hardening

Port the fork's sandbox hardening into upstream
`src/agent/agent-hook-executor.js` through one shared executor used by both
transform scripts and hook logic. Do not interpolate untrusted script text into
a wrapper function, invoke untrusted code outside the timed VM boundary, or
inject host-realm constructors/callables. Exposed intrinsics and facades are
created inside the context; host data is cloned and validated at the boundary.
Regression tests must cover infinite loops and constructor escape through every
exposed object or callable, proving that `process`, `require`, and host globals
remain unavailable.

### Trigger-producer reachability

In `src/config-validator.js`, an `onComplete` contract is valid only when the
agent's top-level `triggers` contain an executable `execute_task` producer path.
Apply that predicate consistently to conductor detection, output recording,
completion-handler reporting, and topic-contract collection. Configuration
validation must reject unreachable completion contracts without rejecting
validators and other legitimate no-task roles that do not advertise completion
output.

### Logical iteration accounting

In `src/agent/agent-lifecycle.js`, increment `agent.iteration` once for each
logical trigger execution, not once for each provider retry. Provider retry,
recovery, continuation, and terminal bounds stay upstream-owned. Reaching the
maximum enters an explicit synthesis/terminal phase rather than scheduling a
global delayed stop.

### Exactly-one terminal lifecycle

Review and drafting packs require time to synthesize their bounded final
artifact. One cluster-scoped terminal coordinator owns the durable phase state,
deadline timer, `AbortController`, publisher dependency, and idempotency key.
Every agent, subcluster, provider-failure path, artifact owner, and orchestrator
fatal path for that artifact workflow uses the same authority. The workflow
operation dispatcher receives its signal and reports success, failure, or
cancellation back through this API. Generic clusters retain upstream
max-iteration behavior. A success, max-iteration, synthesis failure,
cancellation, or fatal error converges on one idempotent terminalization
boundary which publishes exactly one terminal event. Do not restore the fork's
old ten-minute delayed stop timer.

`begin` returns the closed terminal execution claim, including execution key,
absolute deadline, disposition, and the coordinator-owned abort signal. Final
operation code receives that exact signal; deadline/cancel cannot be represented
by a separate controller.

The foundation provides this as an opt-in primitive only; the later workflow
layer classifies a sealed artifact descriptor and installs it. Generic upstream
clusters never acquire the coordinator.

Add `workflow_state` to the ledger database, keyed by cluster, workflow
instance, and state key. One ledger transaction compare-and-set updates its
versioned state and optionally inserts a deterministic row into the existing
unchanged v6.46 `messages` table; semantic/input/output digests stay in bounded
workflow state, avoiding a messages-schema migration. Those messages are the
durable outbox. Terminal transition
and complete success/failure envelope commit together. Live delivery occurs
after commit. Workflow state tracks pending/delivered disposition; start/resume
may re-deliver committed unfinished work, so live delivery is at-least-once and
consumers are idempotent while the ledger event remains exactly-once. The
terminal record contains execution key, phase, start time,
absolute deadline, artifact identity/sequence/checksum, optional handoff key,
and terminal envelope/digests. Resume re-arms only the remaining deadline and
reuses the same execution key; an expired synthesis atomically fails once.

### Claude overlay fail-closed behavior

Retain upstream's owned, private, per-run Claude settings overlay in
`src/worktree-claude-config.ts`. It must remain owner-checked, mode-checked,
canonical-path checked, and cleanup-owned. If the small hardening is still
needed, make `isMutableRecord` reject arrays. Malformed input fails closed; it
is never replaced with an empty settings object. Do not restore global
settings installers.

## Approved preflight quality gate

### Purpose and separation

The preflight gate is an optional, cheap Node-side check of the starting
repository. It runs before any provider/model call. It is not a command proof,
not a protected handoff gate, and not evidence that remains valid after a
workflow changes the tree.

Implementation workflows may additionally use their owned pre-validation
phase after implementation and before validators. Protected
`requiredQualityGates` remain enforced by the upstream handoff boundary and
have no bypass.

### Data model

Store one approved record per canonical repository root under the existing
`~/.zeroshot/projects/` state directory. Use a versioned record:

```ts
interface ApprovedPreflightGateV1 {
  version: 1;
  repositoryPath: string; // realpath of canonical git root
  command: string; // exact human-approved shell command
  fingerprint: string; // sha256 of discovery inputs + command
  discovery: 'deterministic';
  approvedAt: string; // full ISO-8601 timestamp
}
```

Configuration filenames remain keyed by the SHA-256 hash of the canonical
repository path, preserving the fork's existing external state location while
making the record explicit and fail-closed. A malformed, mismatched-path, or
unknown-version record is treated as no approved gate.

### Discovery and approval state machine

`discoverPreflightGate(repositoryRoot)` is deterministic and side-effect free.
It inspects bounded, known ecosystem files and returns either one composed
command plus its input fingerprint or no suggestion. It must not invoke a
model, execute package scripts, scan outside the repository root, or write
state.

Before provider startup:

1. `--skip-quality-gate` returns `skipped` without discovery or execution.
2. A valid deterministic cached record executes only when both its exact
   command and fingerprint equal the current deterministic suggestion. When
   discovery now returns no suggestion, a valid existing cached command still
   runs, as required by ADR 0009. Manual records are outside this milestone
   unless an equally deterministic source and invalidation manifest are defined.
3. A new or changed deterministic suggestion in an interactive TTY is shown
   verbatim and requires one-time confirmation. Acceptance atomically saves the
   exact record, reloads and validates it, then executes it and returns a
   receipt; a second invocation prompts zero times.
4. A changed suggestion in a non-interactive run always fails before provider
   startup. `--allow-missing-quality-gate` applies only when no valid cached
   command and no deterministic suggestion exists; it never authorizes a
   changed command.
5. No cached record and no deterministic suggestion is the same missing-gate
   state: interactive runs may continue after an explicit no-gate confirmation;
   unattended runs require `--allow-missing-quality-gate`.
6. Refusal, gate failure, timeout, cancellation, or launch error aborts before
   any provider call.

LLM-assisted discovery, if later exposed, may only print a suggestion for a
human to copy into the same approval flow. It never caches, authorizes, or
executes its answer.

### Execution boundary

The runner receives a validated record and canonical root, then invokes the
approved command in that root with:

- a fixed timeout;
- cancellation propagation;
- bounded captured stdout and stderr with truncation markers;
- an explicit minimal environment allowlist (including required platform and
  toolchain variables), with secret-shaped variables excluded before spawn;
- an owned cross-platform process tree: a dedicated POSIX process group and
  Windows tree termination, with bounded TERM/KILL escalation;
- no template-controlled environment or cwd; and
- a structured result (`passed`, `failed`, `timed_out`, `cancelled`, or
  `launch_error`).

The approved command is intentionally a shell string because the human is
approving the exact repository gate. No template can set it. The implementation
must not reuse `execute_system_command` or expose this runner as a trigger
action.

### Launch-path propagation

Add both CLI flags to the maintained run-option types and serialize them
through foreground, detached daemon, worktree, Docker, resume, and trusted
worker boundaries. The gate runs once against the original repository before
isolation setup or a model call. The CLI issues the receipt for local starts;
the trusted cluster-worker adapter leaves the public request unchanged and runs
the gate locally from registry-owned policy. `Orchestrator.start` accepts only
an internally issued receipt or a reference resolved from private run state.
This is an ordering boundary inside the trusted local product, not
authentication against arbitrary code execution. Daemon children consume a compact attestation
(status, root, fingerprint, timestamps, exit code, truncation flag, and optional
owned diagnostic reference/digest), never captured stdout/stderr in an
environment variable.

`--skip-quality-gate` and `--allow-missing-quality-gate` affect only this
preflight subsystem and optional pack pre-validation. They are never mapped to
or allowed to remove `requiredQualityGates`.

## Closed workflow-operation boundary

### Why a separate boundary exists

The historical `execute_system_command` action served two unrelated purposes:
quality checks and deterministic artifact/context processing. Quality checks
move to the dedicated boundaries above. The remaining behavior becomes typed,
in-process runtime operations, so templates cannot name executables, pass
shell, select cwd, inject environment variables, or route arbitrary stdout.

### Trigger contract

Add one closed action to configuration validation and the trigger dispatcher in
`src/agent/agent-lifecycle.js`:

```ts
type WorkflowOperationId =
  | 'review.synthesize'
  | 'document.build_revision_context'
  | 'document.assemble';

interface ExecuteWorkflowOperationAction {
  action: 'execute_workflow_operation';
  operation: WorkflowOperationId;
}
```

No `command`, `args`, `cwd`, `env`, `stdin`, `onSuccess`, or `onFailure`
routing field is accepted. Each registered operation owns its input topics,
ledger queries, output schema, success topic, failure topic, and whether the
result is terminal. Unknown IDs and extra fields fail configuration validation.

### Runtime interface

```ts
interface WorkflowOperationContext {
  clusterId: string;
  agentId: string;
  triggeringMessage: Message;
  ledger: LedgerReader;
  signal: AbortSignal;
  now(): Date;
}

type WorkflowOperationResult = {
  state: 'ready';
  content: { text: string; data: Record<string, unknown> };
};

type WorkflowOperation = (context: WorkflowOperationContext) => Promise<WorkflowOperationResult>;
```

Operations run only after a provider-free host coordinator has deterministically
established readiness; quorum waiting is not an operation result. Registry
descriptors own routing and use terminal policy `never`, `immediate`, or
`after_artifact_commit`; review synthesis and final document assembly use the
last policy so successful terminalization cannot precede artifact acceptance.

The registry is a frozen record of descriptors keyed by `WorkflowOperationId`.
Each descriptor fixes allowed input topics, snapshot/query policy, output
validator, success and failure topics, and terminal capability; templates and
implementations cannot override those fields. The executor builds context from
`agent.cluster.id` and a read-only facade over `agent.messageBus`, binds every
ledger read to `triggeringMessage.sequence`, and uses the terminal coordinator's
abort signal. Results pass through the ordinary message bus and common
terminalization boundary. Exceptions are bounded, redacted, and converted to
the descriptor's failure event; they do not crash the orchestrator or execute
fallback shell.

The resolved host workflow instance, not model output, owns family/config
revision and expected identities. Direct packs seal this immutable descriptor
at initial resolution. Conductors persist an unfinalized root descriptor, then
atomically seal it exactly once from the validated dynamic config before loaded
agents or republished input can run; operations reject an unsealed descriptor.

Operation output identity is semantic. Review synthesis keys one transition by
workflow instance, config revision, review ID, round, and operation ID; the
trigger message/cursor/digest are conflict evidence. The executor owns atomic
ledger/message-bus `publishIfAbsent`, returning inserted/reused/conflict and
notifying subscribers only for inserted. The terminal coordinator durably
claims and arms its absolute deadline before operation code runs, so a hanging
operation is bounded. Its versioned CAS record persists execution key, phase,
absolute deadline, artifact receipt, and terminal message ID; resume reuses the
same key and remaining deadline.

A cluster-owned provider-free `WorkflowRuntime` is installed from the sealed
descriptor before product agents run (or immediately after a conductor seals
its dynamic config). It owns family reducers, durable ready claims, catch-up,
and operation authorization. A template ready trigger is accepted only when its
sender/ID/key/digest/cursor match the durable host claim. Review and final
document assembly enter terminal synthesis before execution; nonterminal
revision-context uses its own bounded operation claim and ordinary cluster
cancellation without changing terminal phase.

Ledger `workflow_state` is canonical for unfinalized/sealed descriptor,
coordinator/progress phase, artifact binding/path/cursor, and handoff. Cluster
JSON is only a derived summary. Resume calls `hydrateWorkflowRuntimeFromState`
immediately after ledger/message-bus creation and before rebuilding agents,
registering subscriptions, starting providers, or replaying outbox rows.

### Owned operations

- `review.synthesize` reconstructs analyst/validator history and produces one
  Markdown review artifact with confirmed, contested, and withdrawn findings,
  validator notes, severity changes, statistics, and readiness.
- `document.build_revision_context` reconstructs the current document and
  aggregates only the latest validator round into the next drafter context.
- `document.assemble` deterministically applies the full first draft plus later
  deltas, adds notes and unresolved validator reasons, and produces one
  Markdown document artifact.

The old `scripts/write-review-report.js`, `scripts/build-revision-context.js`,
`scripts/assemble-doc.js`, `scripts/quality-gate-runner.js`, and generic
`execute_system_command` tests are prior art. Their shell/stdin/environment
protocols are not retained.

## Specialized workflow packs

### Shared pack contract

Restore code review, documentation review, and document drafting under
`cluster-templates/` as parameterized opt-in configurations. Each family has a
base plus its named specialists and conductor. Generic upstream templates and
`conductor-bootstrap.json` remain unchanged as defaults.

All packs share:

- explicit schemas for every inter-agent message;
- deterministic topic and producer reachability;
- a conservative fixed batch instruction. For this MVP it is an explicit
  prompt-level policy, not a claimed runtime semaphore over provider-native
  subagents;
- no autocompact environment injection;
- no generic command trigger;
- a bounded analyst/revision count;
- an explicit synthesis phase and exactly one terminal event;
- simulation coverage for random ordering and topology; and
- a declaration that the successful result is exactly one Markdown artifact.

Before provider startup, `validateArtifactWorkflowConfig` binds that declaration
to exactly one reachable final operation: matching descriptor success topic,
`after_artifact_commit` policy, correct family, and no competing producer. The
immutable binding flows through the sealed descriptor, runtime, final-operation
`ArtifactReadyPayload`, and writer; artifact identity is host-derived rather
than model-authored.

Review messages use a shared versioned envelope with family-specific payloads.
Every candidate and verdict carries workflow/review ID, round, finding ID,
candidate revision, validator identity, causation/idempotency key, and a durable
snapshot cursor. One provider-free persisted round coordinator consumes
schema-checked analyst-complete envelopes (including explicit empty results),
owns expected analysts/validators, zero-findings behavior, retry/failure
treatment, frozen snapshot, round-scoped claim, and the exactly-once
`REVIEW_ROUND_READY` transition. Its aggregation table defines confirmed,
contested, withdrawn, severity-change, and missing-validator outcomes.
Envelope quorum fields are redundant assertions checked against the immutable
host-owned workflow instance.

The document reducer likewise waits for the sealed validator quorum and frozen
revision snapshot. It atomically emits `DOCUMENT_REVISION_READY` below cap when
revision is required, or `DOCUMENT_ASSEMBLY_READY` on unanimous approval or at
cap. LLM/template messages cannot choose that deterministic branch.

Adaptive concurrency is excluded. A later design may reserve four machine
threads and preserve a two-worker floor, but must also consider provider,
harness, memory, and configured maxima.

### Code-review pack

Restore the base workflow and Bell, Book, Candle, and conductor roles. Analysts
produce candidate findings; validators may confirm, contest, withdraw, or
adjust severity. At the iteration cap, synthesize the truthful report rather
than assuming approval:

- any contested finding makes the overall result `NOT_READY`;
- confirmed, contested, and withdrawn sections remain distinct;
- validator reasons and severity changes remain visible; and
- the cap is a normal bounded terminal reason, not a validation verdict.

Zero findings must produce a valid, explicit ready report rather than waiting
for a message that can never be produced.

### Documentation-review pack

Restore the base workflow and Trace, Vector, Axiom, and conductor roles. It
uses the same contested-finding terminal semantics as code review, but its
finding schema and prompts are documentation-specific. The two pack families
share synthesis primitives, not templates or message schemas.

### Document-drafting pack

Restore the base workflow and Facet, Lens, Prism, and conductor roles. The first
`DRAFT_READY` owns the complete document; later iterations contain explicit
deltas. Each message carries document ID, revision, base revision, validation
round, causation/idempotency key, and snapshot cursor. A delta may target only
the current base revision; stale/future messages are rejected and retry replay
is idempotent. Reconstruction order is deterministic and stable across retries.

If validators unanimously approve, assemble an `ALL_APPROVED` artifact. If the
revision cap is reached, assemble the best document with termination
`MAX_ITERATIONS` and append conspicuous unresolved sections containing each
validator verdict and reason. The incomplete draft remains useful but is never
labelled approved.

## Deterministic `--output` contract

`zeroshot run --output <file>` is separate from upstream's foreground benchmark
`--result-file`. It is accepted only when the fully resolved configuration
declares exactly one Markdown artifact.

At the initial CLI boundary:

1. capture the original invocation cwd;
2. resolve a relative destination against it;
3. append `.md` only when the final path component has no extension;
4. reject incompatible workflows before provider startup; and
5. persist the absolute destination in run state for foreground, detached,
   resumed, worktree, and Docker paths.

Artifact persistence is an awaited, replayable phase before successful
terminalization. Persist `ARTIFACT_READY` with exact Markdown, checksum,
destination identity, and sequence; the host-side owner commits through a
private sibling temporary file and records `ARTIFACT_COMMITTED`; only then may
the success terminal event be published. Resume replays READY without COMMITTED
idempotently. Commit failure produces the sole failure terminal. Create missing
parent directories, leave an existing destination unchanged on failure, and
print the resolved path only after COMMITTED.

When `--output` is absent, the same owner validates and persists
`ARTIFACT_ACCEPTED` before terminal success; no filesystem commit is attempted.
For dynamically loaded artifact workflows, disable the upstream generic
completion-detector/git-pusher terminal path so validation cannot stop the
cluster before artifact acceptance/commit.

Classification occurs from the root artifact declaration before initial
`--pr` completion injection, and is checked again at dynamic load. Persist one
protected handoff descriptor and activate it exactly once only after
`ARTIFACT_ACCEPTED` or `ARTIFACT_COMMITTED`; early validation cannot release it.

For `--pr`/`--ship`, acceptance/commit enters durable `HANDOFF_PENDING` rather
than terminal success and inserts one host-owned `ARTIFACT_HANDOFF_READY` only
after an idle protected pusher is subscribed. The pusher reads the stored
artifact/handoff evidence, not historical validation trigger timing. The
coordinator remains sole terminal publisher; only verified PR/merge completion
may complete handoff. Without delivery mode, acceptance/commit proceeds directly
to success.

A distinct deterministic artifact-handoff pusher configuration has sole trigger
`ARTIFACT_HANDOFF_READY`, a provenance-bound handoff key/receipt, and no raw
terminal/publish-after action. PR verification requests completion only through
`completeHandoff`; the ordinary upstream pusher remains unchanged for generic
workflows.

Artifact persistence is an orchestrator/runtime responsibility, not an
operation script side effect. The operation returns Markdown in its typed
result; the artifact writer owns filesystem mutation.

This atomic replacement contract is not a sandbox against a concurrently
malicious same-UID process replacing destination ancestors. Partial lexical or
`lstat` checks would not close that race; a stronger threat model requires a
separate descriptor-relative/OS-specific design.

## Post-reconciliation subagent visibility

### Activation

Compute one immutable capability before the first provider launch:

```ts
interface SubagentTelemetryCapability {
  enabled: boolean;
  reason: 'foreground_tty' | 'detached' | 'daemon' | 'silent' | 'worker' | 'resume' | 'non_tty';
}
```

Only a run launched in a supported foreground TTY with the status footer gets
`enabled: true`. Resume, later attach, `logs -f`, detached, daemon-only, silent,
and worker paths never create telemetry files or install tracking hooks.
Provider support is a separate per-parent capability; one unsupported provider
must not disable telemetry for supported parents in the same foreground run.

### Provider-neutral event sink

Use a Zeroshot-owned per-run directory with private permissions and one
append-only JSONL file per parent agent. The normalized record is:

```ts
interface SubagentLifecycleEvent {
  version: 1;
  event: 'start' | 'stop';
  provider: 'claude' | 'codex';
  parentAgentId: string;
  parentInvocationId: string;
  providerSessionId?: string;
  providerTurnId?: string;
  providerToolUseId?: string;
  childAgentId: string;
  agentType: string;
  title?: string;
  occurredAt: string; // full ISO-8601
}
```

The hook writer validates fixed-size stdin, event name, scalar lengths, parent
and invocation identity supplied by the owned overlay, output path containment,
ownership, mode, and regular-file status. It serializes writers through a
private per-file lock with a bounded fail-open timeout, opens without following
symlinks where supported, validates the opened descriptor, and performs the
size check and complete bounded append while holding the lock. Invalid or
overflowed telemetry exits successfully without affecting the provider.
Consumer-observable corruption or cap exhaustion closes affected rows; a silent
append/lock failure is inherently unobservable and is bounded by durable
provider-task completion or final parent completion.

The consumer reads only complete newline-terminated records, caps file size,
record size, active children, displayed rows, and retained stopped entries,
and deduplicates transitions by
`(provider, parentAgentId, parentInvocationId, childAgentId)`.
Partial/malformed/late records are ignored or retained for the next read.
Provider-task completion closes one invocation while permitting a later
invocation by the same parent; final parent completion rejects all later events.
Use the durable Zeroshot provider `taskId` as `parentInvocationId`.
`task-lib/runner.js` is the sole allocator and adds it to final provider env
after generation. Both watcher variants share a best-effort session observer
that runs only after authoritative task persistence; observer failure cannot
change task outcome. It writes a bounded root-session control record into the
same parent file, and the tracker may defer lifecycle rows until that binding
arrives. The foreground CLI allocates one idempotent telemetry
resource handle before cluster start and releases it in a `finally` covering
startup, streaming, and shutdown. Preparation/mount failures attributable only
to telemetry roll back partial resources, warn once, and continue with telemetry
disabled.

### Claude producer

Extend the existing `src/worktree-claude-config.ts` overlay only for an enabled
run. Merge Zeroshot's `SubagentStart` and `SubagentStop` commands into the
owned overlay without mutating user files or dropping unrelated settings.
Claude's documented hook events supply `agent_id` and `agent_type`; transcript
paths and final messages are deliberately ignored.

Current Claude Code permits nested subagents. Use a bounded `PostToolUse Agent`
spawn-link record: hooks in the root caller lack `agent_id`, hooks in a nested
caller carry it, and the successful response identifies the spawned child.
Buffer lifecycle rows until exact same-session child-ID linkage proves the root
caller; non-root links are descendants and remain hidden. Missing/conflicting
links fail closed. The same proven link may carry a terse bounded description
as title. No ordering inference or transcript parsing is permitted.

Pin the hook-specific official Agent response schema: `completed` and
`async_launched` responses include `agentId`. If a probed supported CLI omits it
or it does not match the lifecycle `agent_id`, classify that parent as
unsupported and render no Claude rows; the generic Agent SDK result type is not
used for hook correlation.

### Codex producer

Create an owned Codex config layer beside the run's private config, using
documented `hooks.json` or inline hook configuration and the existing adapter's
`--config` support. Codex discovers hooks from active config layers and still
runs matching hooks from other layers; Zeroshot must not suppress or bypass
their review/trust behavior.

Use documented `SubagentStart` and `SubagentStop` records for lifecycle. Accept
a direct child only when the event's provider session matches the root session
captured by the adapter; use turn/tool-use IDs for correlation and late-event
rejection. To get the orchestrator-assigned `task_name`, observe the owned
`PostToolUse` record for `spawn_agent` and correlate its returned child
identifier. `task_name` is a constrained snake-case routing identifier, not
free-form prose; a bounded underscore-to-space display transform is allowed,
but assignment messages/transcripts are never captured. If a supported literal
response cannot correlate one child ID, show `agent_type`. Do not restore PR
31's incidental JSON collaboration-stream parser.

Hook compatibility is capability-detected without a model call through a
separate private evidence schema; it is not folded into the generic help/version
feature detector. Distinguish config-compatible, disabled by user/policy,
config rejected, handler unavailable, and unknown. Official tooling has no
machine-readable exact-definition trust status, so compatibility never implies
trusted. Negative/unknown evidence omits overrides; compatible launches allow
Codex's normal trust layer to run or skip the hook without changing the task.

Codex trust has an explicit user-invoked bootstrap: build the exact immutable
host hook definition used in production, verify the packaged handler,
and open an interactive no-prompt Codex TUI for the user to review it through
`/hooks`. Zeroshot never records trust itself or uses the global bypass. A
changed definition requires review again.
The CLI owns `zeroshot telemetry trust-codex-hooks`; it requires a TTY, verifies
the package handler, uses the exact production builder, opens a no-prompt Codex
TUI with inherited stdio, and persists neither config nor trust state.

Codex-in-Docker telemetry is excluded from this MVP because no documented
mapping proves that host-reviewed exact-definition trust applies in-container.
It degrades to no telemetry; Claude Docker telemetry remains supported.

### Footer integration

The foreground CLI owns the tracker because it already owns TTY detection,
`StatusFooter`, and the render lock; the orchestrator never renders directly.
Create the run telemetry root before Docker isolation and apply its validated
host/container mapping through one helper used by the main container and late
validator-fallback container. Resume has no footer/tracker ownership path and is
always telemetry-disabled. Enabled Claude containers mount the exact current
standalone hook at a constant absolute path; Codex containers receive no
telemetry override, env, or mount. Mounts cannot be added later. The CLI feeds normalized child state
into the existing `StatusFooter`; do not create a second renderer. Child rows
are visually subordinate to their direct parent,
show a bounded title/type and elapsed state, and do not participate in process
metrics sampling. Footer row caps and terminal-size degradation remain
upstream-owned. Final cleanup stops provider launches/tasks, performs one final
complete-record poll, closes invocations/parents, stops the footer, and removes
only the owned telemetry root.
